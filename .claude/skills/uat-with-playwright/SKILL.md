# 受け入れ条件を Playwright で 1 行ずつ確かめる

渡された条件を、ブラウザで実際に操作して 1 つずつ「満たす / 満たさない / 判定できない」に分け、理由とスクリーンショットを付けて報告する。コードは直さない。

## 0. 準備

- Playwright MCP のツールは遅延読み込みなので、最初に `ToolSearch` で `select:mcp__playwright__browser_navigate,mcp__playwright__browser_snapshot,mcp__playwright__browser_click,mcp__playwright__browser_type,mcp__playwright__browser_fill_form,mcp__playwright__browser_take_screenshot,mcp__playwright__browser_evaluate` を読み込む（ダイアログが出る操作なら `browser_handle_dialog` も）。
- アプリが起動しているかを `curl -s -o /dev/null -w "%{http_code}" http://localhost/` で確かめる。落ちていれば `./vendor/bin/sail up -d`。
- スクリーンショットの置き場 `uat-shots/` を作る（`mkdir -p uat-shots`）。
- ログインに使うアカウントは指示に従う。指示がなければシーダーの `usera@example.com` / `userb@example.com`（パスワード `password`）。ログイン画面にも書いてある。
- **条件ごとに、どのユーザーで・どのポストで確かめるかを先に決める。** 「他人の〜」を確かめるには、別ユーザーのデータが画面に出ている必要がある。リプライ付きのポストなどは、画面を総当たりせず読み取り専用で探す。
    ```bash
    ./vendor/bin/sail artisan tinker --execute='echo json_encode(\App\Models\Reply::selectRaw("post_id, user_id, count(*) c")->groupBy("post_id","user_id")->get());'
    ```
    出力の先頭に出る `Restricted Mode: ...` の行は無視してよい。

## 1. 操作の進め方

- 操作の前後に `browser_snapshot` を取り、要素の `ref` はその都度スナップショットから取る（ページが変わると `ref` は変わる）。判定の根拠は、見た目より先にスナップショットの文字（見出しの件数、本文、ボタンの有無）に置く。
- 証拠は `browser_take_screenshot` で `uat-shots/` に保存する。`fullPage: true`、`scale: "css"`。
- ファイル名は「どの行のものか」が分かるようにする: `<行番号 2 桁>-<内容>.png`（例: `02-reply-added.png`）。同じ行で複数枚あるときは `04a-`, `04b-` と枝番を付ける。同じ状態を指す写真が複数枚できてもよいが、報告ではどれが何を示すかを書く。
- ユーザーを切り替えるときは、ログアウトボタンを押してから `/login` で入り直す。

## 2. 条件の種類ごとの確かめ方

- **一覧・詳細が見える**: 既存データのあるページを開き、見出しの件数と本文が出ていることを確かめる。0 件のページで「一覧が見える」と判定しない。
- **追加できる**: 送信前後の件数（「リプライ(n)」など）を比べる。並び順の決まりがあれば（`CLAUDE.md`: 新しい順）、そこまで見る。
- **入力エラーが出る**: 空のまま送信し、次の 2 段で確かめる。
    1. そのまま押す。入力欄に `required` があると、ブラウザ標準の吹き出し（「このフィールドを入力してください。」）が先に出てサーバーまで届かない。吹き出しはスクリーンショットにもスナップショットにも写らないので、`browser_evaluate` で `validationMessage` と `required` を読んで根拠にする。
    2. サーバー側の検証と、アプリ自身のエラー文言を見るため、`browser_evaluate` でフォームの `noValidate = true` にしてから押す。コードは変えない。画面に日本語のメッセージが出て、件数が増えないことを確かめる。
    報告では 1 と 2 を分けて書く。吹き出しだけで「エラーが表示された」と済ませない。
- **自分のものだけ消せる**: 自分の行には削除ボタンがあり、他人の行にはないことを、**両方のユーザーで**確かめる（A から見た B の行、B から見た A の行）。消す操作は、この確認のために自分で作ったデータにだけ行う。
- **URL 直打ちで 403 になる**: 本物のデータを消す可能性があるので、ブラウザでは試さない。ボタンが隠れるところまでを確認範囲にし、「403 は未確認（`ReplyTest` 等のテストで見る）」と報告に書く。必要なら人に確認してから、使い捨てのデータで行う。

## 3. データの後始末

- 確認のために作ったデータ（送信したリプライなど）は、同じ手順の中で消して元に戻す。消す操作自体が確認項目なら、それで兼ねる。
- 戻したことを件数で確かめる。戻せなかったものは報告に書く。
- Playwright MCP は作業ディレクトリに `.playwright-mcp/`（ログとスナップショット）を作り、`git status` で未追跡に出る。報告の最後に、消すか `.gitignore` に入れるかを人に決めてもらうよう書く。勝手に消さない。

## 報告の形

条件ごとに 1 行、表にする。

| # | 判定 | 理由 | スクリーンショット |
| - | ---- | ---- | ------------------ |

- 判定は **満たす / 満たさない / 判定できない**。注意があるときは「満たす（注意あり）」とし、表の下に注意を書く。
- 理由は、画面で見えた事実（件数の変化、出た文言、ボタンの有無）と、どのユーザー・どのポストで見たか。
- スクリーンショットは `uat-shots/` のファイル名で、何を示すかが分かるようにする。
- 表のあとに **確認していないこと**（403 の直打ち、他のブラウザ幅、など）と **後片付け**（戻したデータ、`.playwright-mcp/`）を分けて書く。
- 確かめられなかったことを「満たす」にしない。足りないものを書いて「判定できない」にする。

## やらないこと

- アプリのコード・設計書・テストを直さない。満たさない条件が出たら、報告して人に渡す。
- 本物（シーダー由来）のデータを、確認のために消さない・書き換えない。
- `answers/` は読まない（`CLAUDE.md` の決まり）。
