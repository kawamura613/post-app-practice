# PR を設計書と突き合わせて読む

PR の差分を、設計書（`docs/*.md`）→ 触らないはずの場所 → 中身 の順に読み、観点ごとの表で報告する。コードは直さない。直すかどうかを決めるのは人なので、この Skill の仕事は「どこを見れば判断できるか」を渡すところまで。

順番に意味がある。設計書との突き合わせを先にやると、「書いていないものが増えていないか」という全体の枠が決まり、そのあとの細かい読みが枠の内か外かで迷わない。中身の読みを最後にするのは、枠の外の変更ほど人が見るべき度合いが高く、そこに時間を割きたいから。

## 0. 対象を決める

- PR 番号が引数にあればそれを使う。ない、または `<番号>` のような未置換の文字が残っているときは `gh pr list --state merged` で一覧を出す。候補が 1 件ならそれを対象にして、どの PR を読むかを報告に書く。複数あるときは聞く。
- 次を取る。
    ```bash
    gh pr view N --json title,body,baseRefName,headRefName,mergeCommit,additions,deletions,changedFiles
    gh pr diff N --name-only
    gh pr diff N > <scratchpad>/prN.diff      # 1000 行を超えることがあるので一度ファイルに落とす
    ```
- **行番号はマージ時点のもので出す。** main はその後も動くので、現在のファイルの行番号は PR の差分とずれる。`git show <mergeCommit.oid>:<path> | grep -n ...` で確定させ、報告には「行番号はマージ時点」と書く。未マージなら head ブランチ。
- 設計書は PR の本文（`Closes #N`）や `docs/` の `Issue: #N` から探す。見つからなければ判定の基準がないので、そのことを報告の冒頭に書き、1 の列は「判定できない（設計書なし）」にする。
- 設計書が PR 時点から変わっていないかを `git diff <mergeCommit.oid> HEAD -- docs/<file>` で確かめ、変わっていれば報告に書く。

## 1. 設計書と突き合わせる

設計書の次の節を、差分の実際の変更と 1 つずつ照らす。

- 「受け入れ条件」「増えるテーブル」「増える画面」「入力チェックとメッセージ一覧」: 設計書どおりに実装されているか（列・ルート・文言）。
- 「変えないもの」と、設計書が「作らない」と書いたもの: 差分がそこに触っていないか。
- **設計書に書いていないものが増えていないか。** `--name-only` の一覧から、設計書の画面・テーブル・テスト観点のどれにも対応しないファイルを洗い出す。`composer.json` / `composer.lock`（依存の追加）、`CLAUDE.md`、設定ファイル、他機能のテストは特に目を留める。差分に入っていないことも「OK（差分になし）」として報告に残す。
- **PR 本文の主張を差分で裏取りする。** 「既存メソッドは無変更」「テスト N 件通過」のような一文は、差分と食い違っていることがある。食い違いは要確認。テスト結果は自分で回していなければ「判定できない（実行していない）」とする。

## 2. 触らないはずの場所を見る

「変えないもの」から、触らないはずのファイルを具体的に挙げて読む。この repo では多くの場合 `routes/web.php`、`app/Http/Controllers/PostController.php`、`app/Policies/PostPolicy.php`、`resources/views/posts/index.blade.php` だが、機能ごとに設計書の「変えないもの」から選び直す。

- **消えた行（`-`）から先に読む。** 追加行は新機能のものだが、消えた行は今ある動きを壊す可能性がある。消えた行が何で、同じ中身で戻っているか（インデントだけの変更か）、意味が変わっていないか（`@csrf`・`@method`・`@can`・`with()` が残っているか）を確かめる。
- 消えた行が 0 の追加だけの変更も、読んだ結果として「OK」と残す。ルートなら、新しい `/posts/{post}` 系が既存の固定パス（`/posts/create` など）を飲み込まない並びかも見る。
- 変更されていない（差分にない）のに「触らない」と指定されたファイルは、「OK（差分になし）」とする。
- 見た目の変化（余白・表示条件）はテストが HTML 文字列しか見ていないと確認できない。画面を見ていなければ「判定できない」と書き、何が足りないか（ブラウザで 2 ユーザーを切り替える、など）を添える。

## 3. 中身を読む

`CLAUDE.md` の Architecture 節をチェックリストの出どころにして、次の観点を読む。

- **N+1**: ビューが引く関連が、コントローラーの `with()` / `load()` に入っているか（差分で確かめる）。`@can` が内部でクエリを打たないかも見る。
- **認可の置き場所**: コントローラーの `$this->authorize(...)` とビューの `@can` の両方があるか。Policy の判定が「`user_id` が本人か」のみで揃っているか。
- **マスアサインメント**: `$fillable` の中身と、`create` / `update` に渡している配列の出どころ（`$request->all()` でなく `validate()` の戻り値か。`user_id` をサーバー側で決めているか）。
- **XSS**: `{!! !!}` や `style=` / `href=` / `<script>` に入る値がエスケープ・定数由来か。
- **CSRF**: 送信フォームと `@method` 付きの削除フォームに `@csrf` があるか。ルートが `web` グループか。
- **入力チェック**: 必須・上限・日本語メッセージ（`validate()` の第 2 引数）が揃っているか。`config/app.php` の `locale` が `en` なので、メッセージを指定していない項目は英語になる。新しく足したルールにメッセージが付いているか。CRLF → LF の置換の有無、`old()` で入力が残るかも見る。
- **書き方の揃い**: 周りのコードと命名・コメント量・テストの書き方が揃っているか。コピーされた重複（同じ検証コードが 2 か所、同じ配列が 2 つのビュー）は、値が一致しているかまで確かめて報告する。

読み終えて確信が持てない観点は、無理に OK にしない。「何が足りなくて判定できないか」を必ず書く（実機で動かしていない、他のファイルを見ていない、など）。

## 報告の形

観点ごとに 1 行、表にする。列はこの順。

| 観点 | 判定 | 場所 | 気づいたこと |
| ---- | ---- | ---- | ------------ |

- 判定は **要確認 / OK / 対象外** の 3 つ。判定できないときは判定欄に「判定できない」と書き、気づいたことに足りないものを書く。
- 場所は `ファイル名:行番号`（マージ時点）。差分に現れないものは「(差分になし)」。
- 気づいたことは事実と根拠を 1 文で。「こうすべき」の提案より、「設計書のこの行と食い違う」「ここが消えた」のように、人が確かめられる形で書く。
- 表は「1. 設計書との突き合わせ」「2. 触らないはずの場所」「3. 中身」の 3 つに分ける。冒頭に対象の PR（番号・タイトル・マージ commit）と、行番号がマージ時点であること、設計書をどの版で見たかを 1〜2 行で書く。
- 最後に **「人が自分の目で読むべき場所」を 3 つまで** 挙げる。選ぶ基準は、要確認のうち設計書の枠の外にあるもの、消えた行があるもの、判断が人にしかできないもの（意図した変更か、設計書と PR 本文のどちらを直すか）。3 つに収まらなければ優先度で絞る。

## やらないこと

- コードや設計書を直さない。直す提案が必要なら、報告のあとで人が決めてから。
- テストを回さない（頼まれたときだけ）。PR 本文のテスト結果は「本文の記載」として扱う。
- `answers/` は読まない（`CLAUDE.md` の決まり）。
